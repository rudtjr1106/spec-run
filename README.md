# spec-run

Claude Code 스킬입니다. 짧은 요청을 **완료 기준이 담긴 계획 프롬프트**로 바꿔 보여줍니다. 승인하면 구현하고 **같은 턴에서 검증까지** 끝냅니다.

```text
/spec-run 장바구니 합계에 쿠폰 할인 추가해줘
```

## 무엇을 위한 스킬인가

Claude Code에 "쿠폰 할인 추가해줘"처럼 짧게 시키면 이런 일이 생길 수 있습니다.

- 무엇을 어디까지 만들지 정하지 않은 채 파일부터 고칩니다.
- "다 됐습니다"라고 하는데 테스트를 돌렸는지 알 수 없습니다.
- 커밋하고 나서야 깨진 것을 발견합니다.

spec-run은 작업 순서를 하나로 고정합니다.

1. 완료 기준이 들어간 계획을 먼저 보여준다
2. 사람이 승인한다
3. 계획한 범위만 구현한다
4. 마지막 수정 뒤에 검증 명령을 실행한다
5. 완료 기준별로 근거를 붙여 보고한다

## 설치

Claude Code가 설치돼 있어야 합니다. 명령은 macOS, Linux 셸 기준입니다. Windows에서는 Git Bash에서 실행하세요.

모든 프로젝트에서 쓰려면 개인 스킬 폴더에 받습니다.

```bash
git clone https://github.com/rudtjr1106/spec-run.git ~/.claude/skills/spec-run
```

폴더 이름은 `spec-run` 그대로 두세요. 설치한 뒤 Claude Code 세션을 새로 열면 `/spec-run`이 보입니다. 같은 폴더가 이미 있으면 clone이 실패합니다. 이미 설치했다면 아래 업데이트 명령을 쓰세요.

### 한 프로젝트에서만 쓰기

프로젝트 루트에서 받습니다. 프로젝트가 git 저장소라면 받은 폴더가 저장소 안의 저장소가 되므로 아래 둘 중 하나를 고릅니다.

혼자 쓸 때는 받은 폴더를 내 로컬에서만 무시합니다.

```bash
git clone https://github.com/rudtjr1106/spec-run.git .claude/skills/spec-run
```

```bash
echo ".claude/skills/spec-run/" >> .git/info/exclude
```

팀과 공유할 때는 `.git`을 지우고 프로젝트 저장소에 파일로 커밋합니다.

```bash
git clone --depth 1 https://github.com/rudtjr1106/spec-run.git .claude/skills/spec-run
```

```bash
rm -rf .claude/skills/spec-run/.git
```

```bash
git add .claude/skills/spec-run
```

`.git`을 지우지 않고 `git add` 하면 폴더가 내용 없는 링크로만 올라갑니다. 다른 사람이 받은 저장소에는 스킬 파일이 없게 됩니다.

### 업데이트와 삭제

```bash
git -C ~/.claude/skills/spec-run pull
```

```bash
rm -rf ~/.claude/skills/spec-run
```

프로젝트에 설치했다면 경로를 `.claude/skills/spec-run`으로 바꿉니다. 스킬이 저장한 계획서는 삭제해도 `~/.claude/plans/`에 남습니다. 이 스킬이 만든 파일은 이름이 `.plan.md`로 끝납니다.

## 사용법

### 1. 요청하기

```text
/spec-run 장바구니 합계에 쿠폰 할인 추가해줘
```

Claude가 코드를 읽어 고칠 파일을 찾습니다. 그리고 지금 상태에서 검증 명령을 한 번 실행해 이미 실패하는 테스트가 있는지 확인합니다(최대 2분). 그다음 아래 같은 계획 프롬프트를 코드 블록 하나로 출력하고 멈춥니다. 아래에서는 이 블록을 계획 블록이라고 부릅니다.

이 단계에서는 소스 파일을 고치지 않습니다. 검증 명령이 만드는 빌드 산출물(`build/`)은 생깁니다. 아래는 Android 샘플 프로젝트에서 실제로 나온 계획을 줄여서 보인 것입니다.

````text
[spec-run 계획] 장바구니 합계에 쿠폰 할인(정액·정률) 추가

## 목표
`total()`에 쿠폰을 넘기면 상품 합계에서 할인액을 뺀 뒤 배송비를 계산해 반환한다. 쿠폰을 넘기지 않으면 지금과 똑같이 동작한다.

## 대상 파일
- `cart/src/main/kotlin/com/example/cart/Cart.kt` — `sealed interface Coupon`(`Fixed`, `Percent`)과 `discount()` 추가, `total()`에 `coupon: Coupon? = null` 매개변수 추가
- `cart/src/test/kotlin/com/example/cart/CartTest.kt` — 쿠폰 테스트 5개 추가(기존 3개는 그대로)

## 제약
- 대상 파일만 수정한다.
- `total()`의 기존 매개변수 순서와 기본값은 유지한다.
- `build.gradle.kts` 등 빌드 설정과 의존성은 건드리지 않는다.

## 가정
- 무료배송 여부는 쿠폰 적용 후 금액으로 판단한다(50,000원에 10% 쿠폰이면 45,000원 + 배송비 3,000원 = 48,000원).
- 정률 할인은 1원 미만을 버린다.
- 최소 주문 금액, 유효기간, 최대 할인 한도는 이번 범위에 넣지 않는다.

## 완료 기준
1. 정액 쿠폰이 상품 합계에서 차감된다: `total(listOf(Item(10000, 1)), coupon = Coupon.Fixed(2000))` == 11000 — 확인: `CartTest.fixedCouponSubtractsFromSubtotal`
2. 무료배송은 할인 후 금액으로 판단한다: `total(listOf(Item(50000, 1)), coupon = Coupon.Percent(10))` == 48000 — 확인: `CartTest.freeShippingUsesDiscountedSubtotal`
3. 쿠폰 없이 호출하면 결과가 그대로다 — 확인: 기존 테스트 3개가 수정 없이 통과
4. 아래 검증 명령이 통과해야 한다.

## 검증 명령
```bash
./gradlew test
```

## 마무리
커밋하지 않는다

위 계획대로 구현하고, 마지막 수정 뒤에 검증 명령을 실행해 완료 기준을 하나씩 확인한 결과를 보고해.
````

실제 계획에서는 샘플의 CLAUDE.md에 적어 둔 `JAVA_HOME=<JDK 17 경로>` 접두가 검증 명령 앞에 붙어 있었습니다. 기기마다 다른 경로라 예시에서는 뺐습니다.

요청에 없어서 Claude가 정한 것은 질문하지 않고 `가정`에 적습니다. 마음에 들지 않는 줄은 고쳐서 보내면 됩니다. 질문으로 끝나는 경우는 둘뿐입니다. 고칠 파일을 하나도 찾지 못했을 때와 `/spec-run`만 보내고 요청을 쓰지 않았을 때입니다.

대상 파일이 3개 이상이거나 추가하거나 삭제하는 줄이 합쳐 100줄을 넘을 것 같으면 같은 계획을 `~/.claude/plans/<날짜-시각>-<제목>.plan.md`에도 저장합니다. 프로젝트 밖 홈 폴더에 쓰는 파일이고 승인 전에 저장됩니다.

계획 블록 아래에는 안내 줄이 붙습니다.

| 안내 줄 | 나오는 때 |
|---|---|
| `이 블록을 복사해 /spec-run 없이 그대로(또는 고쳐서) 보내면 실행합니다.` | 항상 |
| `계획서 저장: <경로>` | 계획서를 파일로 저장했을 때 |
| `이 세션은 대상 저장소 폴더에서 시작되지 않아 …` | 세션 폴더가 git 저장소가 아니거나 대상 파일이 그 밖에 있을 때 |
| `이 앱에서 입력한 프롬프트는 probe-your-ai-ability 1.0.3이 …` | 터미널 `claude`가 아닌 곳(데스크톱 앱, IDE 확장 등)에서 실행할 때 |

마지막 줄은 probe-your-ai-ability를 쓰지 않아도 나옵니다. 필요 없으면 `SKILL.md`에서 그 줄을 지우세요.

### 2. 승인하기

| 보내는 것 | 결과 |
|---|---|
| 계획 블록 그대로 | 그 계획대로 실행 |
| 계획 블록을 고친 것 | 고친 내용이 최종 계획. 바로 실행 |
| 계획이 나온 직후의 "진행", "ㅇㅇ" | 마지막에 출력한 계획대로 실행 |
| "ㅇㅇ 근데 정률만 지원해"처럼 내용을 바꾸는 말 | 코드는 고치지 않고 그 말을 반영한 계획을 다시 출력하고 멈춤. 다시 승인해야 실행 |

짧은 승인으로도 실행되지만 스킬이 먼저 권하지는 않습니다.

### 3. 결과 받기

Claude는 계획한 파일만 고칩니다. 마지막 수정 뒤에 검증 명령을 실행하고 이런 표로 보고합니다.

| 완료 기준 | 결과 | 근거 |
|---|---|---|
| 1. 정액 쿠폰이 상품 합계에서 차감된다 (11000) | 충족 | `CartTest.fixedCouponSubtractsFromSubtotal` 통과 |
| 2. 무료배송은 할인 후 금액으로 판단한다 (48000) | 충족 | `CartTest.freeShippingUsesDiscountedSubtotal` 통과 |
| 3. 쿠폰 없이 호출하면 결과가 그대로다 | 충족 | 기존 테스트 3개 통과, `git diff`에서 `CartTest.kt`의 삭제 줄 없음 |
| 4. 검증 명령이 통과한다 | 충족 | `./gradlew test` 결과 `BUILD SUCCESSFUL`, 4개 변형 모두 실패 0 |

결과 칸은 `충족`, `미충족`, `미확인` 중 하나입니다. 표 아래에 변경 파일과 미충족, 미확인 항목의 이유가 붙습니다.

검증이 실패했을 때는 이렇게 합니다.

- 이번 변경이 원인이면 고치고 검증 명령을 다시 실행합니다.
- 이번 변경과 무관하게 원래 깨져 있던 테스트면 건드리지 않고 그대로 보고합니다.
- 테스트를 지우거나 skip하지 않고, 실패하는 테스트를 빼는 옵션도 붙이지 않습니다.

구현하다가 계획에 없는 파일을 고쳐야 한다는 것이 드러나면 편집을 멈춥니다. 이미 고친 것이 있으면 검증 명령부터 실행합니다. 그런 다음 대상 파일을 고친 계획 블록을 다시 출력합니다. 이 계획을 다시 승인하면 이어서 진행합니다.

### 커밋까지 맡기기

요청에 커밋을 넣으면 계획의 `마무리` 칸에 브랜치와 커밋 메시지가 들어갑니다. 푸시나 PR 생성을 요청했으면 그것도 적힙니다.

```text
/spec-run 쿠폰 할인 기능 추가하고 커밋까지 해줘
```

```text
## 마무리
검증 통과 후 `feat/coupon-discount`에서 `feat: 장바구니 합계에 쿠폰 할인 추가`로 커밋한다
```

프로젝트 지침(CLAUDE.md 등)에 커밋, 푸시, PR 규칙이 있으면 요청에 쓰지 않아도 `마무리`에 들어갑니다. 원하지 않거나 브랜치가 다르면 그 줄을 고쳐서 보내세요.

커밋은 검증 명령을 실행해 통과했거나 새로 실패한 테스트가 없을 때만 합니다. 원래 깨져 있던 테스트만 실패하면 그 사실을 보고하고 커밋합니다. 검증이 실패했으면 커밋하지 않고 보고에 적습니다. `git add`는 계획한 파일만 올립니다.

## 쓰면 좋은 점

Android 샘플 프로젝트(라이브러리 모듈 1개, 플레이버 `dev`/`prod`, 변형 4개)에서 같은 기능 요청을 두 방식으로 2번씩 실행했습니다. 한쪽은 "질문하지 말고 바로 구현해줘"를 붙인 요청이고 다른 쪽은 `/spec-run`입니다.

| 항목 | 바로 구현 (2회) | spec-run (2회) |
|---|---|---|
| 정책 결정이 드러나는 시점 | 구현이 끝난 뒤 최종 메시지 | 코드를 쓰기 전 계획의 `가정` |
| 무료배송 기준 | 실행마다 달랐음(할인 후 금액, 할인 전 금액) | 2회 모두 할인 후 금액 |
| 요청에 없던 기능 | 한 실행이 최소 주문 금액과 최대 할인 한도를 추가 | 추가 없음. 범위 밖 항목은 `가정`에 명시 |
| 바뀐 파일 | 4개, 3개 (둘 다 새 파일 2개 생성) | 계획에 적힌 2개 |
| 구현 뒤 검증 명령 | `./gradlew :cart:test`, `./gradlew :cart:testDevDebugUnitTest :cart:testProdDebugUnitTest` | `./gradlew test` |
| 검증 범위 | 실행마다 달랐음(변형 4개, debug 변형 2개) | 2회 모두 같음(변형 4개) |
| probe-your-ai-ability 검증 인식 | 2회 모두 인식되지 않음 | 2회 모두 인식됨 |
| 보고의 근거 | 통과한 테스트 개수 | 완료 기준마다 테스트 이름과 결과 |

이 표를 읽을 때는 세 가지를 감안하세요.

- 표본이 2회씩이고 "바로 구현" 쪽은 질문하지 말라는 문구를 붙인 조건입니다. 그 문구 없이 요청했을 때나 Claude Code의 plan mode와는 비교하지 않았습니다.
- 스킬이 결정을 통일해 주는 것은 아닙니다. 계획에서 미리 보여 고칠 수 있게 할 뿐입니다. 널 허용 여부나 정수 연산 방식 같은 구현 세부는 spec-run에서도 구현 뒤에 보고됐습니다.
- 전 변형을 도는 것이 검증이 더 강하다는 뜻은 아닙니다. 이 샘플은 변형별 소스가 없어 네 변형이 같은 테스트를 돌립니다. spec-run이 전 변형을 도는 이유는 분석 도구가 인식하는 형태가 그것이기 때문입니다.

아래는 이 차이를 만드는 스킬의 지시 내용입니다. 훅처럼 기술적으로 막는 장치는 들어 있지 않습니다. 지금까지의 실행에서 어긴 경우는 없었습니다. 확실히 막아야 하면 Claude Code의 권한 설정을 함께 쓰세요.

- 정책 결정을 코드보다 먼저 봅니다. 무료배송 기준, 단수 처리, 잘못된 값 처리처럼 요청에 없는 결정이 `가정`에 한 줄씩 나옵니다. 틀린 줄을 고쳐서 승인하면 구현한 뒤 되돌리는 일이 줄어듭니다.
- 변경 범위를 승인한 계획에 묶도록 지시합니다. `대상 파일` 밖을 고쳐야 하면 편집을 멈추고 계획을 다시 냅니다. 샘플 실행에서는 바뀐 파일이 계획의 대상 파일과 같았습니다. 멈추고 다시 계획하는 경우는 실행해 보지 않았습니다.
- 검증 명령이 계획에 고정됩니다. 승인 턴은 계획의 `검증 명령`을 그대로 실행하므로 실행할 때마다 확인 범위가 달라지지 않습니다.
- 변경 전 상태를 먼저 잽니다. 계획 단계에서 검증 명령을 한 번 실행해 원래 깨져 있던 테스트를 `가정`에 적습니다. 구현 뒤에 실패가 나오면 내 변경 때문인지 구분할 수 있습니다. 검증 명령이 2분 안에 끝나는 프로젝트에서만 해당합니다.
- 실패를 숨기지 않도록 지시합니다. 테스트를 지우거나 skip하지 않고, `-x test` 같은 제외 옵션을 붙이지 않습니다. 기대값은 완료 기준이 요구할 때만 바꾸고 보고에 적습니다.
- 검증하고 나서 커밋합니다. 순서는 편집, 검증, `git add <대상 파일>`, 커밋입니다. `git add -A`를 쓰지 않아 대상 파일 밖의 변경을 새로 스테이징하지 않습니다. 다만 미리 스테이징해 둔 변경과 대상 파일 안에 있던 다른 수정은 같은 커밋에 들어갑니다. 커밋까지 맡길 때는 작업 트리를 비우고 시작하세요.
- 보고에 테스트별 근거가 붙습니다. Gradle은 성공하면 콘솔에 테스트 이름을 찍지 않습니다. 샘플 실행에서는 `build/test-results/`의 결과 XML을 읽어 기준마다 어떤 테스트가 통과했는지 적었습니다.
- 조건이 되면 코드 리뷰가 붙습니다. 한 번의 실행에서 3개 파일 이상을 고쳤거나, 그 대화의 편집 횟수가 합쳐 5회 이상인데 아직 리뷰한 적이 없을 때입니다. 별도 에이전트에게 맡기고, 에이전트 도구를 쓸 수 없으면 `code-review` 스킬로 대신합니다. 계획 범위 안의 지적만 고치고 범위 밖 지적은 보고에 적습니다.

## Android 프로젝트에서 쓰기

spec-run은 계획의 검증 명령을 분석 도구가 인식하는 `./gradlew test`, `./gradlew check`, `./gradlew build` 중 하나로 적습니다. 셋 중 무엇을 고를지 정한 규칙은 없고, 샘플 실행에서는 모두 `./gradlew test`가 나왔습니다.

샘플 프로젝트에서 각 명령이 무엇을 실행하는지 `--dry-run`으로 확인했습니다(Gradle 8.13, AGP 8.12.3, 라이브러리 모듈 1개, 변형 4개).

| 명령 | 실행되는 것 | 태스크 수 | probe-your-ai-ability 인식 |
|---|---|---|---|
| `./gradlew test` | 모든 모듈, 모든 변형의 단위 테스트. release 변형 포함(샘플에서는 `testDevDebugUnitTest` 등 4개) | 79 | 인식 |
| `./gradlew check` | 위 + lint(샘플에서는 `devDebug` 하나) + 프로젝트가 `check`에 연결한 태스크 | 113 | 인식 |
| `./gradlew build` | 위 + 전 변형 assemble | 184 | 인식 |
| `./gradlew test -p cart` | 한 모듈의 전 변형 단위 테스트 | 79 | 인식 |
| `./gradlew :cart:test` | 위와 같음 | 79 | 인식 안 됨 |
| `./gradlew :cart:testDevDebugUnitTest` | 한 변형의 단위 테스트 | 21 | 인식 안 됨 |
| `./gradlew assembleDevDebug` | 한 변형 빌드. 테스트 없음 | 32 | 인식 안 됨 |

`./gradlew lint`와 `./gradlew connectedAndroidTest`도 인식되는 형태가 아닙니다. 옵션은 태스크 뒤에 붙여야 인식됩니다. `./gradlew test -q`는 인식되고 `./gradlew -q test`와 `./gradlew clean test`는 인식되지 않습니다.

### 실행 시간

- 모듈과 변형이 많을수록 `./gradlew test`가 오래 걸립니다. 루트에서 실행하면 모든 모듈의 모든 변형을 컴파일하고 테스트합니다. 이 명령은 계획 단계에서 한 번, 구현 뒤에 한 번 이상 실행됩니다. 샘플은 첫 실행이 19초였고 실제 앱에서는 재 보지 않았습니다.
- 계획에 `check`나 `build`가 나오면 승인 전에 확인하세요. 앱 모듈에서는 `build`가 release 변형 빌드까지 포함합니다(샘플은 라이브러리 모듈이라 이 부분은 확인하지 못했습니다). `test`로 고쳐서 승인하면 됩니다.
- 범위를 줄이려면 `./gradlew test -p <모듈 폴더>`를 씁니다. 그 모듈만 돌고 인식도 유지됩니다. `./gradlew :app:testDevDebugUnitTest`처럼 변형까지 좁히면 실제 검증은 되지만 probe-your-ai-ability에는 잡히지 않습니다. 계획 블록의 `검증 명령` 줄을 고쳐서 승인하는 방식인데, 이 경로는 아직 실행해 보지 않았습니다.
- 계획 단계의 실행은 2분에서 끊습니다. 넘으면 `가정`에 "기준 상태 미확인"이라고 적고 계획을 냅니다. 모듈이 많은 앱은 여기에 걸릴 수 있고, 그러면 원래 깨져 있던 테스트를 미리 구분해 주지 못합니다.

### 원래 깨진 테스트가 있을 때

Gradle은 태스크 하나가 실패하면 남은 태스크를 실행하지 않습니다. 모듈 2개짜리 샘플에서 앞 모듈에 깨진 테스트를 두고 확인했습니다. `./gradlew test`는 앞 모듈에서 멈춰 뒤 모듈의 테스트를 돌리지 않았고, `./gradlew test --continue`는 끝까지 돌렸습니다. `--continue`를 뒤에 붙인 형태도 인식됩니다.

이 상황에서 spec-run은 4회 모두 검증 명령에 `--continue`를 붙였습니다. 뒤 모듈의 테스트가 실제로 돌았는지 결과 XML로 확인한 뒤, 깨진 모듈은 건드리지 않고 대상 파일만 커밋했습니다. 처음 2회는 스킬에 이 규칙이 없을 때였고, 지금은 스킬 본문에 명시돼 있습니다.

### 검증이 확인해 주지 않는 것

- `./gradlew test`는 `androidTest` 소스를 컴파일하지 않습니다. 계측 테스트가 깨져도 통과합니다.
- 단위 테스트가 없는 모듈에서는 `./gradlew test`가 사실상 컴파일 확인입니다.
- JVM 테스트로 확인할 수 없는 완료 기준(테스트가 없는 Compose 화면 등)은 스킬 지침상 보고에 `미확인`으로 남습니다. `미확인`이 있어도 검증 명령이 통과하면 `마무리`의 커밋은 진행됩니다. 이 경우는 실행해 보지 않았습니다.

### JDK 경로

`JAVA_HOME=/path ./gradlew test`처럼 값에 공백이 없는 환경변수 접두는 인식됩니다. `JAVA_HOME=$(/usr/libexec/java_home -v 17) ./gradlew test`는 인식되지 않습니다.

샘플에서는 CLAUDE.md에 적어 둔 접두가 계획의 검증 명령에 그대로 붙었습니다. 접두 없이 쓰려면 `gradle.properties`에 `org.gradle.java.home`을 지정합니다. 샘플에서 그렇게 하니 `JAVA_HOME` 없이도 지정한 JDK로 Gradle 데몬이 떴습니다. 기기마다 경로가 다르면 각자의 `~/.gradle/gradle.properties`에 둡니다.

## 토큰 사용량

고정으로 드는 것은 두 가지입니다.

- 스킬 본문은 약 5,500토큰으로 추정합니다. `/spec-run`을 부를 때 컨텍스트에 올라갑니다. 부르지 않는 세션에는 스킬 설명 한 줄만 올라갑니다. 측정에서는 본문을 읽은 직후 컨텍스트가 7.6k 늘었는데, 스킬을 읽지 않은 에이전트도 첫 호출 뒤에 약 2k가 늘어서 그만큼을 뺀 값입니다.
- 계획 블록 하나는 약 1,500~2,000토큰입니다. 출력으로 한 번, 승인하려고 다시 보낼 때 입력으로 한 번 듭니다.

Android 샘플에서 같은 기능을 구현했을 때의 측정값입니다(2회 평균).

| | API 호출 | 턴에서 새로 쌓인 컨텍스트 | 캐시에서 다시 읽은 입력 |
|---|---|---|---|
| 바로 구현 | 7.0회 | 18.1k | 383k |
| spec-run 계획 턴 | 5.5회 | 14.1k | 303k |
| spec-run 승인 턴 | 6.0회 | 17.4k | 361k |

정리하면 이 샘플에서 spec-run은 작업 하나에 다음만큼 더 들었습니다.

- API 호출은 7.0회에서 11.5회로 약 1.6배입니다. 측정에서는 계획 에이전트가 스킬 본문을 읽는 데 호출을 한 번 썼고, 이를 빼면 약 1.5배입니다.
- 캐시 읽기는 383k에서 664k로 약 1.7배입니다. 호출마다 컨텍스트 전체를 캐시에서 다시 읽기 때문입니다. 이 측정에서 에이전트의 기본 컨텍스트는 약 5.2만 토큰이었고, 설치한 스킬과 커넥터 수에 따라 달라집니다.
- 새로 쌓인 컨텍스트는 3~4k 많았습니다. 스킬 본문과 측정 환경의 고정분을 빼고 계획 블록 두 벌(약 3.5k)을 더하면 spec-run이 약 19.7k, 바로 구현이 약 16k입니다. 차이 가운데 약 1.7k는 승인 에이전트가 소스 파일을 다시 읽은 분량입니다.

이 수치의 한계는 다음과 같습니다.

- 출력 토큰은 표에 넣지 않았습니다. 실행 기록에 최종 출력량이 일부 호출에만 남아 있어 합계가 실제보다 작게 나옵니다. 파일 2개를 쓰고 2개를 고친 호출이 8토큰으로 기록돼 있었습니다.
- 계획 턴과 승인 턴을 서로 다른 에이전트로 실행했습니다. 그래서 스킬 본문과 소스 파일을 두 번 읽었습니다. 한 세션에서 이어서 쓰는 경우는 재 보지 않았습니다.
- 성공한 실행만 잰 값입니다. 빌드가 실패해 다시 도는 경우는 재지 않았습니다.
- 리뷰가 붙으면 가장 많이 듭니다. npm 샘플에서 5개 파일을 고친 실행의 승인 턴은 API 호출 14회, 캐시 읽기 약 100만 토큰이었습니다. 리뷰가 없던 승인 턴은 5~8회, 24만~50만 토큰이었습니다.

줄이려면 이렇게 합니다.

- 한 줄 수정처럼 작은 일은 스킬 없이 시킵니다.
- 계획을 승인할 때 `/spec-run`을 다시 붙이지 않습니다. 붙이면 스킬 본문이 한 번 더 올라갈 수 있습니다(재 보지 않았습니다).
- Gradle 출력을 줄입니다. 샘플에서 `./gradlew test`는 성공 시 81줄(약 4KB)을 출력했고, `./gradlew test -q`는 성공 시 아무것도 출력하지 않았습니다. 샘플 실행에서는 Claude가 `2>&1 | tail -40`을 붙여 실행했습니다.

## 알아둘 점

- Claude Code의 plan mode와는 비교하지 않았습니다. spec-run이 더하는 것은 완료 기준이 들어간 계획 양식, 같은 턴의 검증, 기준별 보고입니다.
- probe-your-ai-ability를 쓰지 않는 팀은 Gradle 표준 형태를 지킬 이유가 없습니다. `SKILL.md`의 검증 명령 표에서 Gradle 줄을 팀 CI가 쓰는 명령으로 바꾸세요.
- `/spec-run` 없이 "계획서 먼저 보여줘"처럼 요청하거나 `[spec-run 계획]`으로 시작하는 블록을 보내도 이 스킬이 실행될 수 있습니다.
- spec-run이 도는 동안에는 브레인스토밍이나 계획 실행용 다른 스킬의 질문 절차를 따로 시작하지 않습니다.
- 테스트 러너가 없는 폴더에서는 임시 확인 명령(`node -e …` 등)으로 대신합니다. 이때는 계획의 `가정`에 "러너 없음 — 임시 확인"이라고 적습니다.
- Gradle은 모듈 1개와 2개짜리 Android 라이브러리 샘플에서만 실행해 봤습니다. 앱 모듈이 있는 실제 프로젝트에서는 실행해 보지 않았습니다.

## probe-your-ai-ability 기록에 남는 것

[probe-your-ai-ability](https://www.npmjs.com/package/probe-your-ai-ability)는 AI 코딩 도구의 로컬 사용 기록을 읽어 활용 방식을 수치로 내는 도구입니다. 이 도구는 정해진 형태의 행동만 인식합니다. spec-run은 실제로 한 검증과 계획이 그 형태로 남도록 맞춰져 있습니다.

| 도구가 보는 것 | spec-run이 하는 일 |
|---|---|
| 편집한 턴 안에서 마지막 편집 뒤에 실행된 검증 명령 | 승인 턴 안에서 마지막 수정 뒤에 검증 명령을 실행 |
| 편집과 커밋 사이의 검증 | 검증한 뒤에만 커밋 |
| 큰 편집 전의 계획 증거 | 조건이 되면 계획서를 `~/.claude/plans/*.plan.md`로 저장 |
| 편집이 많은 세션의 독립 리뷰 | 조건이 되면 리뷰 에이전트(없으면 `code-review` 스킬) 실행 |
| 경로, 완료 기준, 제약 같은 단서가 두 가지 이상 담긴 편집 시작 프롬프트 | 사용자가 계획 블록을 `/spec-run` 없이 직접 보내 승인 |

계획 블록은 `/spec-run`을 붙이지 않고 보내세요. 붙여도 실행은 되지만 도구가 슬래시 명령으로 분류해 편집 시작 프롬프트로 세지 않습니다. "진행" 같은 짧은 승인도 실행은 되지만 단서가 없는 짧은 프롬프트로 기록됩니다.

검증으로 인식되는 주요 명령 형태는 다음과 같습니다(1.0.3 기준).

| 프로젝트 | 인식되는 형태 |
|---|---|
| Gradle | `./gradlew test`, `./gradlew build`, `./gradlew check` |
| npm, pnpm, yarn, bun | `npm test`, `npm run lint`, `npm run typecheck`, `npm run build` |
| Python | `pytest`, `ruff`, `mypy`, `pyright` |
| JS 도구 직접 실행 | `vitest`, `jest`, `tsc`, `eslint`, `playwright` |
| Go, Rust, .NET | `go test`, `cargo test`, `dotnet test` (`build`, `check`, `vet`, `clippy`도 인식) |
| Maven, Make | `mvn test`, `mvn verify`, `make test`, `make lint`, `make check` |

Bash 도구로 실행한 명령만 봅니다. 명령은 이 형태로 시작해야 합니다. 앞에 `cd <폴더> &&`, `npx`, `python -m`, `uv run`, 값에 공백이 없는 환경변수는 붙여도 됩니다.

### 기록의 한계

아래는 스킬 동작이 아니라 probe-your-ai-ability에 기록이 남는지에 관한 내용입니다. 스킬은 어느 경우에나 똑같이 동작합니다.

- 데스크톱 앱에서 입력한 일반 프롬프트는 집계되지 않습니다. 1.0.3은 `promptSource`가 `sdk`인 기록을 사람 프롬프트로 세지 않는데, Claude 데스크톱 앱에서 입력한 프롬프트가 그렇게 기록됩니다. 그래서 "도구가 보는 것" 표의 마지막 줄(편집 시작 프롬프트)은 데스크톱 앱에서는 기록되지 않습니다.
- 데스크톱 앱에서는 `/spec-run`으로 시작해야 나머지가 기록됩니다. 슬래시 명령은 집계되고 턴을 엽니다. `/spec-run`으로 시작했으면 편집 뒤 검증과 큰 편집의 계획이 그 턴에 기록됩니다. 말로 계획을 요청했거나 새 세션에 계획 블록만 붙여 넣으면 열린 턴이 없어 둘 다 기록되지 않습니다. 커밋 전 검증과 리뷰는 세션 단위라 어느 경우에나 기록됩니다.
- 데스크톱 앱에서는 일반 프롬프트가 턴을 나누지 않습니다. `/spec-run` 뒤에 같은 세션에서 한 다른 편집도 같은 턴으로 묶입니다.
- 터미널 `claude`에서 어떻게 집계되는지는 확인하지 못했습니다. 데스크톱 앱 쪽은 패키지 코드와 기기 한 대의 세션 기록 형태를 대조해 확인했습니다.
- 기록이 프로젝트와 연결되려면 세션을 대상 저장소 폴더에서 열어야 합니다. 도구는 세션을 시작한 폴더를 기준으로 프로젝트를 판단합니다.
- 테스트 러너가 없는 폴더의 임시 확인은 검증으로 잡히지 않습니다.
- 집계 규칙은 버전에 따라 바뀔 수 있습니다. 이 문서의 내용은 1.0.3의 패키지 코드를 읽고 확인한 것입니다. 점수 계산은 서버에서 하므로 이 기록이 점수에 어떻게 반영되는지는 확인하지 못했습니다.

## 어떻게 확인했나

작은 샘플 프로젝트 네 가지에서 실행했습니다. npm 프로젝트, 테스트 러너가 없는 폴더, Android 라이브러리 모듈 1개짜리, 2개짜리입니다.

- spec-run 없이는 5번 실행했습니다. npm 프로젝트에서 쿠폰 기능 요청과, 같은 요청에 급하다는 말을 붙인 것을 한 번씩 했습니다. 테스트 러너가 없는 폴더에서는 한 줄 수정을 한 번 했습니다. 이 환경에는 다른 워크플로 스킬(superpowers)이 설치돼 있었고, 기능 요청 2번은 그 스킬의 절차대로 질문으로 끝났습니다. Android 샘플에서는 "질문하지 말고 바로 구현해줘"를 붙인 요청을 2번 했습니다.
- spec-run을 적용해서는 10가지 상황을 18번 실행했습니다. 같은 상황을 여러 번 실행한 것이 섞여 있습니다. 스킬 문서를 고친 뒤 다시 실행한 것이 5번, 같은 문서로 반복한 것이 2번입니다. 5개 파일 변경은 계획 턴과 승인 턴을 따로 실행했습니다.

각 실행은 에이전트에게 스킬 문서를 읽히고 사용자 메시지를 주는 방식이었습니다. 계획 턴과 승인 턴은 서로 다른 에이전트가 맡았고 실제 `/spec-run` 슬래시 호출은 아니었습니다. 결과는 에이전트가 남긴 도구 호출 순서와 실제 파일, git 상태로 확인했습니다. 토큰 수치는 각 에이전트의 실행 기록에 남은 사용량을 합친 것입니다.

| 상황 | spec-run 없이 | spec-run 적용 |
|---|---|---|
| 짧은 기능 요청 | 질문으로 끝나거나 "ㅇㅇ면 진행"을 권함 | 편집 없이 계획 블록 출력 |
| 한 줄 수정 | 계획 없이 바로 편집 | 계획 먼저, 승인 후 편집 |
| 승인 후 구현 | 비교하지 않음 | 계획한 파일만 수정, 마지막 편집 뒤 `npm test` |
| 원래 깨진 테스트가 있음 | 비교하지 않음 | 그 테스트는 건드리지 않고 "기존 실패"로 보고 |
| 커밋 포함 요청 | 비교하지 않음 | 편집, 검증, 대상 파일만 `git add`, 커밋 순서 |
| 5개 파일 변경 | 비교하지 않음 | 계획서 저장, 검증 후 코드 리뷰 수행(에이전트 도구가 없어 `code-review` 스킬로 실행) |
| Android 샘플의 기능 요청 | 모듈이나 변형을 지정한 태스크로 검증 | `./gradlew test`로 4개 변형 검증 |
| Android 2모듈 샘플, 앞 모듈에 깨진 테스트 | 비교하지 않음 | `./gradlew test --continue`로 검증, 대상 파일만 커밋 |

실행해 보지 않은 것도 있습니다.

- 계획 블록을 고쳐서 승인하는 경우
- 구현 중에 계획에 없는 파일이 필요해져 멈추고 계획을 다시 내는 경우
- 계획 단계의 검증 명령이 2분을 넘는 경우, 검증이 길어 백그라운드로 실행하는 경우
- 편집 5회 누적으로 리뷰가 붙는 경우와 에이전트 도구로 띄운 리뷰
- 대상 저장소와 다른 저장소에서 연 세션
- 터미널 `claude`
- 앱 모듈이 있는 실제 프로젝트, 계측 테스트, Compose UI 변경
- 이 실행들을 probe-your-ai-ability로 분석하는 것. 프롬프트와 명령이 인식 규칙에 맞는지는 패키지 코드의 규칙을 옮겨 적은 스크립트로 확인했습니다.
